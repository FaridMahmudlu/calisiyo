## Issues found and fixed

### QA-01 — Medium — Pomodoro could drift, lose state, or double-write a completed focus session

- Reproduce: start a timer, background or refresh the tab, then let it finish; reload again near completion.
- Expected: elapsed time follows wall clock, survives refresh, and creates exactly one study/statistics record.
- Actual: decrement-only state could drift in a background tab, refresh discarded the active timer, and independent inserts were not atomic or idempotent.
- Affected: `app/dashboard/pomodoro/page.js`, `supabase/migrations/20260812143000_qa_data_integrity.sql`.
- Fix: persisted a per-user timer deadline/state, calculated remaining time from the wall clock, captured the study date before midnight, added stable session keys, and introduced one authenticated atomic/idempotent `complete_pomodoro_session` RPC.
- Verification: start/pause/resume/refresh/finish/reload test passed; duplicate reload retained one session only.

### QA-02 — Medium, security — A child record could reference another user's private resource

- Reproduce: as User A, send a direct PostgREST insert with `user_id=A` and a known `kaynak_id` owned by User B.
- Expected: the database rejects the cross-tenant association.
- Actual: RLS checked only the child `user_id`; the old foreign key checked only resource existence. The relationship could also block User B from deleting the resource and expose an existence oracle.
- Affected: `supabase/migrations/20260802132259_create_initial_tables.sql`, `20260804114721_enrich_study_data.sql`, `20260804192008_harden_rls_and_trigger_functions.sql`.
- Fix: `20260812143000_qa_data_integrity.sql` adds a unique `(user_id,id)` resource key and composite same-owner foreign keys for tasks, wrong questions, and study sessions, with safe column-specific `ON DELETE SET NULL`.
- Verification: two disposable authenticated users proved that cross-user reads, resource references, and user-ID impersonation are rejected.
- Human review flag: this changes authorization/data-integrity constraints; the migration was prechecked for mismatches and applied successfully, but it should remain in release review.

### QA-03 — Medium, security — OAuth/recovery callback allowed a normalized cross-origin redirect

- Reproduce: construct a successful callback with `next=/%5Cevil.example`; the decoded `/\\evil.example` passed the prefix checks and WHATWG URL normalization resolved it to an external origin. Forwarded host/proto were also trusted.
- Expected: a successful callback can navigate only to approved routes on Calisiyo's canonical origin.
- Actual: the post-authentication redirect could leave the application origin.
- Affected: `app/auth/callback/route.js`, `.env.example`.
- Fix: exact internal destination allowlist, backslash/control-character rejection, final same-origin validation, and a canonical configured/deployment origin instead of forwarded authority.
- Verification: valid dashboard/reset destinations remain available; malformed and cross-origin candidates fall back internally.
- Human review flag: this is an auth-boundary change and should remain in release review.

### QA-04 — Medium — Invalid and overlapping daily tasks were not protected consistently

- Reproduce: create a task whose end is before its start, a negative/fractional question target, or a time range overlapping an existing task; direct API writes could bypass UI assumptions.
- Expected: clear Turkish validation and identical enforcement for UI and direct database writes.
- Actual: invalid ranges and overlaps could be accepted depending on the caller; concurrent overlap checks were absent.
- Affected: `app/dashboard/gunluk-program/page.js`, `supabase/migrations/20260812143000_qa_data_integrity.sql`.
- Fix: client validation plus database checks, and a per-user/per-date advisory-lock trigger that serializes and rejects overlaps.
- Verification: invalid end time shows a clear error; CRUD and daily/weekly synchronization passed.

### QA-05 — Medium — Practice-exam inputs allowed invalid values and duplicate subject details

- Reproduce: save a negative/zero/over-600 duration, negative or fractional answer counts, click save repeatedly, or insert the same course twice for one exam.
- Expected: integer nonnegative answer counts, duration 1–600, one detail row per course, and one save operation.
- Actual: validation and database constraints did not consistently enforce those invariants.
- Affected: `app/dashboard/deneme-analizi/page.js`, `supabase/migrations/20260812143000_qa_data_integrity.sql`.
- Fix: Turkish form validation, save de-duplication, database checks, and unique `(deneme_id,ders_id)`.
- Verification: `30 doğru / 4 yanlış / 6 boş` produced exactly `29.00 net`; the record appeared in statistics and deletion removed it.

### QA-06 — Medium — Statistics could mix scopes and double-describe the same questions

- Reproduce: select the 30-day/all range while inspecting the weekly goal card, or have both a completed task and a study record describing the same solved set.
- Expected: top metrics follow the selected range, the goal card explicitly uses the last 7 days, and the same work is not blindly added twice.
- Actual: weekly goal progress inherited the selected larger range, and question aggregation could be misleading.
- Affected: `app/dashboard/istatistikler/page.js`.
- Fix: weekly goals now always filter the last 7 calendar days and are labelled accordingly; session/task question totals are merged using the larger corroborating total globally and per day.
- Verification: direct database recomputation matches the UI exactly: 3,365 minutes, 2,843 questions, 65/76 tasks = 86%, and last-seven-day totals of 730 minutes and 605 questions.

### QA-07 — Medium — Topic status changes could leave orphaned or duplicate automatic repeats

- Reproduce: complete a topic, change it back to not started, then complete it again.
- Expected: three unfinished automatic reminders at +1/+7/+30 days, removed on downgrade, recreated without duplicates; completed history is preserved.
- Actual: stale unfinished reminders could remain and repeated completion could create inconsistent schedules.
- Affected: `app/dashboard/konu-takibi/page.js`, `supabase/migrations/20260812143000_qa_data_integrity.sql`.
- Fix: timezone-aware trigger cleanup and a partial conflict rule for idempotent automatic schedules.
- Verification: disposable-user regression observed exactly three unique dates, zero after downgrade, and exactly three after recompletion.

### QA-08 — Medium — Date boundaries depended on the browser/server timezone

- Reproduce: use the app near midnight outside Turkey or render the same data on a UTC server and a local browser.
- Expected: daily records, streaks, current week, and YKS countdown share Turkey's calendar boundary.
- Actual: local `Date` conversion could move a record or streak across a day boundary.
- Affected: `lib/utils/date.js`, `app/dashboard/page.js`, `app/dashboard/layout.js`, `app/dashboard/istatistikler/page.js`.
- Fix: centralized `Europe/Istanbul` calendar keys and calendar-day countdown math.
- Verification: YKS remains 19 June 2027 and displays 311 days on 12 August 2026.

### QA-09 — Medium — Password rules differed across registration, reset, settings, and account API

- Expected: one clear policy and the same message everywhere.
- Actual: several paths only checked length 8, while others relied on HTML attributes or Supabase responses.
- Affected: `lib/utils/password.js`, `app/kayit/page.js`, `app/sifre-yenile/page.js`, `app/dashboard/ayarlar/page.js`, `app/api/account/route.js`.
- Fix: shared 10-character lower/upper/digit/special validation on every app-controlled path.
- Verification: weak and strong cases passed in UI and API-connected flows.

### QA-10 — Medium — Registration could hide consent and falsely show success for a duplicate email

## Human-review items not auto-changed

### HR-01 — Low — Supabase leaked-password protection is disabled

The current Supabase security advisor still reports this single warning. Enabling it is a project-plan/auth-policy decision and can change signup/reset behavior. The app now enforces a strong password on all app-controlled paths, but direct Supabase Auth calls should also be covered by project-level password policy. Review the official remediation before enabling it: <https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection>.

### HR-02 — Low — Email auto-confirm is enabled

Project Auth currently auto-confirms email signups. Disabling it without a configured, monitored SMTP sender could lock real users out, so it was not changed during a safe QA pass. Configure production mail delivery first, then disable auto-confirm and test delivery, expiry, retry, and abuse/rate-limit behavior.

## Prioritized overall health

The application is functionally healthy after the fixes: core authenticated flows, real-data statistics, planning synchronization, mobile layout, and session controls pass end-to-end. The highest-value corrections were:

1. Atomic, persistent, idempotent Pomodoro tracking so time and streak/statistics data stay trustworthy.
2. Database-level tenant ownership enforcement for resource references.
3. Callback destination containment for OAuth and password recovery.

Next release priority is operational rather than code-level: configure production SMTP/email verification and a Supabase server-side password/leaked-password policy, then repeat the external Google consent and long-window recovery-expiry checks.
